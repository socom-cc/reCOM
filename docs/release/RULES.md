# Release lane: rules for the branch `fts`

The branch `fts` reconstructs the release build of the game from the prototype that the
branch `fts-proto` finished. These rules add to `AGENTS.md`; where they differ for release work,
they say so. Decided with the user on 2026-11-20 and 2026-11-25.

## Target and reference

| | Target (release) | Reference (prototype) |
|---|---|---|
| Disc | SCUS-971.34, version 1.00, NTSC | SCUS-972.05 (demo) |
| Executable | `support/SCUS_971.34` | `support/socom.elf` |
| SHA-256 | `5111e776f64611ae1dcdc725f0ce9db660e90e1763e897e8f5b90f7402ce30d1` | `00c9cee7f75b921fda1e848d04f64881b5a0b7841300591cac91371bb23d4f8a` |
| Symbols and debug data | none (stripped) | symbol table and DWARF |
| Ghidra program | `SCUS_971.34`, project path `/socom-release` | `socom.elf`, project path `/socom.elf` |

- Both executables are untracked; each checkout supplies its own copies under `support/`.
- The extracted release disc is user-local, like the emulator and the prototype's disc image.
  Its location is never written into a tracked file.
- The prototype is read-only on this branch: its executable, its Ghidra program, the tracker
  `.agent/RECONSTRUCTION_PROGRESS.json`, its debug data and the type archive
  `support/socom-types.gdt` are reference evidence. `tools/socom.py` stays pinned to the
  prototype and is not a release tool.
- Nothing from this branch is merged into `fts-proto`. Changes travel the other way:
  `fts-proto` -> `fts` -> later game versions.

## Evidence order for the release

1. The release's own instructions, data and references.
2. A pairing with a prototype function (`docs/release/function-map.tsv`). For an exact pair
   the prototype's name, signature and types carry over as facts. For a deviating pair they
   carry over as the starting point, and every difference is read from the release.
3. Strings in the release.
4. Ghidra's decompilation.
5. Guesses, which stay flagged with a short comment.

A quirk of the prototype that the release also has is kept. A quirk the release no longer has is
dropped on this branch, with a line in the module's note.

## Stages

| Stage | What it produces | Done when |
|---|---|---|
| 1. Intake | The target pinned (above) and the disc's facts in `notes/intake.md` | the note is written |
| 2. Comparison | `function-map.tsv`: every release function paired with its prototype function and classed exact, deviating, new or removed; `COMPARISON.md` | a second agent has checked a module's pairs; unsure pairs are settled or listed |
| 3. Names and types | The release Ghidra program named and typed from the pairs and the type archive | the module's functions carry their names; guesses are flagged |
| 4. Reconstruction | `src/` changed per module: deviations applied, new functions written, removed ones dropped; one note per module under `notes/` | a second agent has compared the module's changed functions with the release |
| 5. Build and behaviour check | The port built against the release disc; the behaviour check extended to the missions the demo lacked | the check passes on the commit |
| 6. Joint verification | The user plays; reported defects are fixed | the user closes the pass |

Stages 2 to 4 run module by module; a module can be in stage 4 while another is in stage 2.

## The record

Release work does not use the prototype's tracker. Its record is:

- `docs/release/function-map.tsv` and `docs/release/COMPARISON.md`, generated by
  `python tools/release/compare.py` (never edited by hand; a pair settled by hand goes into the
  tool's inputs so a rerun keeps it);
- one note per module under `docs/release/notes/`: what differs from the prototype, what was
  written, what was guessed, what could not be run;
- the commits.

Workers never accept their own work. A pairing or a source change is checked by a second agent
that did not produce it, and the note names both.

## Classes

- **exact**: the same instructions and layout once address operands are masked.
- **deviating**: the same function with differences. `imm-only` marks pairs where only
  immediates or offsets differ (often a changed structure layout or constant).
- **new**: a release function with no prototype counterpart.
- **removed**: a prototype function with no release counterpart.
- **unsure**: a candidate pair the evidence does not settle. It is not a final class: stage 2
  ends for a module when its unsure pairs are settled or listed in its note.

## Tools and tests

- Release tools live in `tools/release/` and use only the standard library. They refuse an
  executable whose SHA-256 is not one of the two above.
- Their tests live in `tests/release/` and run with the default test suite.
- Scratch output goes under `build/release/`.

## Ghidra

- Two programs are open in the project. Every call names its program; a call without
  `program=` is a defect.
- Writes go to `SCUS_971.34` only. `socom.elf` is never written.
- The no-scripts rule holds. The two reviewed exceptions in
  `docs/reconstruction/GHIDRA.md` are for the prototype and do not extend to the release
  program.
- One writer at a time. A batch of names or types is checked by a second agent before the next
  batch builds on it.

## Stage 3: names

Step one of stage 3 carries function starts, names and a provenance comment into `SCUS_971.34`
with `tools/release/names.py`, through ordinary bridge endpoints (no script):

```powershell
python tools/release/names.py --plan gamez/zArchive        # or: --plan --all
python tools/release/names.py --apply build/release/names/plan-gamez-zArchive.json --dry-run
python tools/release/names.py --apply build/release/names/plan-gamez-zArchive.json --yes [--batch N]
python tools/release/names.py --confirm-saved build/release/names/plan-gamez-zArchive.apply-001.json
```

- **Plan** (any worker; reads both programs, writes nothing to Ghidra): `build/release/names/plan-<module>.json`
  and a summary `.md`, deterministic, with its own digest. A paired function takes the name the
  prototype program gives its counterpart, a flat name in the global namespace
  (`zar::CZAR::NewKey`), plus the mangled symbol as a second label, as the prototype stores them.
  A library function whose pair is exact takes the prototype's name. One whose pair is
  deviating or unsure takes it when it stands in the same place as in the prototype (between
  the same neighbours of its library) or, for a deviating pair, when its callers decide it or a
  second agent's check settled it (a row in `settled-pairs.tsv`); the
  plate says which. The user decided this for the C standard library on 2026-11-26 and for
  every library on 2026-11-27, to keep the release readable; a pair whose library is not known
  stays on exact pairs. A worker who meets such a function still unnamed may name it on the
  same grounds, in the release program when it is the Ghidra writer, and lists it with its
  evidence in its note. Pairs flagged `name-changed`, `split`,
  `merged` or `rename-possible`, unsure pairs and new functions get no name; their plate comment
  names the prototype counterpart. Every function gets a two-line plate comment (`Release map: ...`)
  with class, prototype address and symbol, evidence, flags, owner file and the settling note.
  Boundary differences, starts without an instruction and thunk or no-return differences are
  listed, not fixed. A create is planned only when its body is predictable: `CreateFunctionCmd`
  follows flow from the entry until an existing function entry, so the plan repeats that flow over
  the release image (`tools/release/createflow.py`) and classes each create safe (the body is the
  map extent as things stand), ordered (after the creates its flow falls or jumps into; the apply
  makes those first) or withheld with the reason (padding or other code would join the body, part
  of the extent is unreachable, its extent overlaps a function, it lies in a gap of an existing
  body: `hole`, or `jump-neighbour` when that function jumps to a map start that is no function).
  Creates that other creates flow or jump into are made first. A planned name that is already a
  label at the function's entry is not sent (Ghidra refuses it); the plate says so. `--assume-removed 0x..` plans as
  if a function had been removed by hand; the apply refuses until it is.
- **Review**: a second agent that did not write the plan checks it before anything is applied.
- **Apply**: the coordinator only, after the review: the dry run first, then `--yes`, optionally
  in batches (`--batch N` changed functions; a rerun continues). The tool checks the open
  programs, the release program's recorded SHA-256 and idle analysis, refuses a plan whose digest
  does not match or that was made from another map, writes to `SCUS_971.34` only (addressed by
  its project path `/socom-release`) and never saves. Per function it creates, renames, adds the
  label (after the rename: Ghidra turns a label on a default-named function into its name) and
  writes the plate comment, reading each back; the first failed read-back stops the run. It waits
  for auto-analysis after each create, compares a snapshot of every release function before and
  after, and reports each change it did not make. The report under `build/release/names/` lists
  every write sent, in order, with its answer. A create that still reads back another extent stops the run; the message and the report (`remove_by_hand`) name the function to remove by hand in Ghidra. Any other change after a create (a function that
  appears or vanishes, a body, name, thunk or no-return flag that changes) stops the run too
  (`analysis_changes` in the report); nothing is removed by hand then: check, save, confirm, replan.
  A second run changes nothing.
- **Save**: the coordinator, through the bridge, after a second agent has checked the batch; then
  `--confirm-saved <report>`, which refuses while a function the report says to remove by hand
  still exists, and also records the writes that were sent but stopped the run before their
  read-back if the saved program holds them. After closing without a save, `--discard-unsaved <report>`.
  A planned create that analysis already made with the map's extent gets a `create-by-analysis` row.
- **Record**: `docs/release/ghidra-applied.tsv` (release address, what was applied, the value, the
  source pair, the date, the state), written by the tool for changes that read back. Its rows stay
  `unsaved <report>` until `--confirm-saved` re-reads them and marks them `saved <date>`; no new
  apply starts while unsaved rows exist.

## Stage 3: signatures

Step two of stage 3 carries function prototypes (return type, calling convention, parameter
names and types, varargs) into `SCUS_971.34` with `tools/release/signatures.py`, through
`set_function_prototype` only (no script), so that the decompiler shows members instead of raw
offsets:

```powershell
python tools/release/signatures.py --plan gamez/zArchive        # or: --plan --all
python tools/release/signatures.py --apply build/release/signatures/signatures-gamez-zArchive.json --dry-run
python tools/release/signatures.py --apply build/release/signatures/signatures-gamez-zArchive.json --yes [--batch N] [--classes exact,deviating,mangled]
python tools/release/signatures.py --confirm-saved build/release/signatures/signatures-gamez-zArchive.apply-001.json
```

- **Plan** (any worker; reads both programs, writes nothing to Ghidra):
  `build/release/signatures/signatures-<module>.json` and a summary `.md`, deterministic, with its
  own digest. A pair is planned when its release function exists with the map's extent, is no
  thunk and has no name of its own other than its counterpart's. Its prototype is read from
  `socom.elf` (the Signature line of `get_function_by_address`; names, types and storage from
  `get_function_variables`). Every type it names must exist in the release program at the same
  path with the same size, and be the only type of its name there (the signature parser looks
  types up by name, ignores `.conflict` suffixes and takes C primitive names such as `long` as
  Ghidra's built-in before any type of the program); otherwise the pair is withheld, the summary
  lists the missing types and says how many type names those two parser rules touch. A
  prototype signature that is still Ghidra's default (undefined return, no parameter) gives
  nothing to carry and is listed. Exact pairs form one group; deviating pairs, and C library
  pairs named by their place, form another, taken only with `--classes exact,deviating`; their
  plate comment gets the clause that the signature is the prototype's and a starting point.
  Unsure pairs, other library pairs that are not exact, pairs flagged `name-changed`, `split`,
  `merged` or `rename-possible`, thunks, boundary differences and functions inside another are
  withheld with the reason.
- **What cannot be carried.** `set_function_prototype` recomputes storage from the calling
  convention (custom storage is switched off; `set_variable_storage` changes nothing), never sets
  or clears no-return (differences are listed, not applied: a no-return change reworks flow at
  every call site), cannot read a type or name holding `(`, `)` or `,`, and sets varargs only
  after a fixed parameter. The prototype's `this` is an ordinary first parameter under
  `__stdcall` and travels as one. Its read-back compares the storage of every parameter with the
  prototype's, so a prototype with storage of its own stops the run.
- **Review**: a second agent that did not write the plan checks it before anything is applied.
- **Apply**: the coordinator only, after the review: the dry run first, then `--yes`, optionally
  in batches. The same guards as for names (open programs, recorded SHA-256, idle analysis, plan
  digest and map, no unsaved rows, writes to the release program only, never a save). Per
  function it checks that the live state is the one planned (body, name, signature, and that it
  is no thunk now: a write to a thunk goes to its target), keeps what the function held in the
  report, writes, reads back the whole
  prototype (signature line and every parameter's name, type and storage) and compares it field
  by field; the first mismatch stops the run. Thunks are never written: a thunk of a written
  function must show the predicted signature at once. A snapshot of every release function
  (existence, body, name, thunk flag, signature line with no-return) is compared with the
  expected state after every `--check-every` written functions (default 10), whenever analysis is
  seen running after a write, and at the end; any change the plan did not make stops the run and
  is listed in the report with the writes since the last clean snapshot (`--check-every 1` names
  the write exactly). A second run changes nothing. Every stop says what to do (the report
  repeats it under `what_to_do`): a stop before a write (`StopBefore`) left nothing for that
  function: save, confirm, replan; a stop after a write was sent (`StopAfter`: the convention
  failed after the signature was committed, or the read-back differs) may leave another
  prototype: save and confirm (the record then says what is there), or close without saving and
  discard; a change the plan did not make (`AnalysisStop`) is checked first: if acceptable, save
  and confirm (the change itself is not recorded), otherwise close without saving and discard.
- **Save**: the coordinator, through the bridge, after a second agent has checked the batch; then
  `--confirm-saved <report>`. It marks the report's rows saved and reads every write that was sent
  but not recorded: one that holds the planned value is recorded as saved; one that holds
  something else than before the run is recorded as it is, with the state `saved <date>, not the
  planned prototype (<report>)`, and listed in the output. After closing without a save,
  `--discard-unsaved <report>`, which refuses while the program holds any write of the report and
  restores the names step's plate rows that the report replaced.
- **Record**: `docs/release/ghidra-applied.tsv`, kind `prototype`, value the signature line with
  the storage of each parameter; plate flags replace the function's `plate` row. Rows stay
  `unsaved <report>` until `--confirm-saved`.

### Group mangled: signatures derived from the mangled symbol

A pair whose prototype counterpart still has Ghidra's default signature has nothing to carry, but
the counterpart's Metrowerks symbol in `support/socom.elf` names its scope and every parameter
type (`tools/release/mwmangle.py`, `tools/release/mangledsig.py`). The plan derives a prototype
for each such entry after every withhold rule above, in a group of its own, applied only when
`--classes` names it: `mangled` takes the derived signatures of exact and of deviating pairs,
`mangled-exact` or `mangled-deviating` one of them; the report counts what it took. On the
prototype functions that have a signature and a mangled symbol no derived field (type, `this`,
storage, return) differs; that ground truth holds no function returning a class by value, and
most of its receivers were set by the prototype's stage 3 with rules of the same kind, so it does
not test the hidden-argument checks below.

- **Parameters**: spelled as the prototype program spells them (reference and pointer `T *`,
  const and volatile dropped, `wchar_t` `ushort`, `long` and `long long` `longlong` (the EE long
  is 64-bit: DWARF, and `long_size` 8 in `r5900.cspec`), `signed char` `schar`, the 128-bit type
  `uint16`, a class or enum by its archive name at `/project/<scopes>`). A named type must be the
  only type of its name in the release, at that category. A named type by value must be an enum
  the release program shows (`get_enum_values`): a class by value may travel as the address of a
  caller's copy (`HandleFollowTickHideCheck`, 0x2f5ba0) or in a register (`PNT2D`), and the name
  does not tell. Withheld: missing or ambiguous types, function and member pointers, arrays,
  classes by value, `double`, `long double` and the 128-bit type by value, more than eight GPR
  or FPR arguments, varargs without a fixed parameter, aliases at the counterpart that disagree,
  `@N@` this-adjusting stubs.
- **Hidden arguments**, under every rule: a function returning a class by value takes a hidden
  pointer to the buffer in a0 and a constructor of a class with virtual bases a hidden flag,
  which move every argument up one register. Withheld: the release code reads an argument
  register's entry value beyond the predicted storage (varargs excepted); the counterpart's DWARF
  record returns a class, structure or union by value; a function other than a constructor or
  destructor copies the entry a0 into v0; a return derived from the slot overrides or a
  conversion operator names a class by value.
- **`this`** (the name does not say whether a member is static), the first that applies decides:
  constructor or destructor; const or volatile member; a slot of a prototype `__vt__` table; no
  scope (none); a scope that is positively a namespace (`std`, `Metrowerks`,
  `Metrowerks::details`, an unnamed namespace: an archive category without a type proves nothing,
  `CZBombState` is a class with a nested enum); `operator new`/`delete` (static); the release
  function's own code reads the entry value of the GPR after the declared GPR parameters, unless
  it stores through a0 before any load through it (a static returning a class looks the same,
  `CPickup::GetFirst`). Anything else is undecided and withheld. The plan keeps what the
  prototype's bytes would have decided (`prototype_bytes_this`).
- **Return** (not in the name): constructors and destructors `void *` (a destructor also takes
  a last `short __dtor_flags`); a conversion operator its type; the one return the signed
  overrides of the same vtable slot agree on; else `undefined`.
- **Names and convention**: `this`, `param_N`, `__dtor_flags`; `__stdcall`.
- **Storage** is predicted the Metrowerks way (a0-a3, t0-t3 in order, floats f12-f19) and the
  read-back compares it like the other groups: a difference stops the run.
- **Plate**: every entry of the group needs a plate of the names step and gets the clause
  `signature derived from the mangled symbol <symbol>: this from <evidence>, return type unknown`
  (or the return and its evidence; a receiver from the code rule reads `this inferred from the
  code alone (...)`); the names step's replan keeps that clause. A release function that already
  has another signature is withheld (a derived signature replaces none).
- **Record**: kind `prototype`, the value ends with `[derived from the mangled symbol]`, so a
  derived prototype never reads as one carried from the prototype.

### Placeholder types (only with the user's agreement)

`tools/release/placeholders.py` plans, and can apply, empty structures for the classes and
parameter types the mangled symbols name and no program holds, so that `T *` parses (`--plan`,
`--apply ... --dry-run`, `--apply ... --yes [--batch N]`, `--confirm-saved`, `--discard-unsaved`;
record `docs/release/ghidra-types.tsv`). A type is created only when it is used as a receiver or
through a pointer, is a C identifier, and no type name of the program or other planned name is
the same with case ignored (the move finds its type case ignored, first hit); a name present in
any spelling (hashed, `.conflict`, `/project/unresolved`) is not missing. Per type:
`import_data_types` `struct <Name>;` (the C parser makes a packed empty structure at the root),
then `move_data_type_to_category`; the whole type table is read before and after each write and
must differ by exactly that one type at the planned category (1 byte), or the run stops. A later
real layout switches packing off and grows the same type in place; deleting and recreating it
would turn every parameter that names it `undefined`, and an archive import at the same path
would add a `.conflict` twin.

## Stage 3: function starts

A step between names and signatures gives the map functions the names step left without a
Ghidra function of their own one, with `tools/release/starts.py`, through two ordinary bridge
writes (no script, nothing removed, cleared or saved):

```powershell
python tools/release/starts.py --plan                     # reads build/release/names/plan-all.json
python tools/release/starts.py --apply build/release/starts/plan-starts.json --dry-run
python tools/release/starts.py --apply build/release/starts/plan-starts.json --yes [--batch N]
python tools/release/starts.py --confirm-saved build/release/starts/plan-starts.apply-001.json
```

- **The cases**: map starts without an instruction (`disassemble_bytes` over exactly the map
  extent, then `create_function`), map functions inside another Ghidra function and creates the
  names step withheld (`create_function` only), and boundary differences (no write: fixed by one
  of those creates, accepted, or not possible).
- **What Ghidra does** (plugin 6.0.0 and Ghidra 12.1.4, read from the classes):
  `disassemble_bytes` runs `DisassembleCommand(range, null, flag)` where the flag is the request's
  `restrict_to_execute_memory`, which the plugin passes as followFlow (`FunctionService.disassembleBytes`);
  the tool always sends false, so only fall-through is disassembled: every undefined address of
  the range, defined data skipped, a run ends silently at an identical existing instruction
  (`CodeManager.checkInstructionSet`, DUPLICATE), a fall into data or into bytes that do not decode
  leaves a "Bad Instruction" bookmark, an existing instruction met as a delay slot is re-made, and
  a run goes on past the range while its last instruction falls through (`Disassembler`). It then
  notifies auto-analysis (`codeDefined`): "Subroutine References" (`FunctionAnalyzer`) creates a
  function at every call target that is none (a one-byte place-holder where there is no
  instruction: `CreateFunctionCmd.getFunctionBody`), "Shared Return Calls" turns jumps to function
  entries into call-returns, and the operand-reference analysis may define data or disassemble
  where the new code points. `create_function` with `disassemble_first` false runs
  `CreateFunctionCmd`: the body follows flow over instructions only and is taken out of an
  existing function it overlaps (`subtractBodyFromExisting`); then, for the new function and every
  function whose body changed, `SharedReturnAnalysisCmd` (contiguous functions assumed, the
  default) turns jumps to the new entry into call-returns and makes Ghidra create a function at
  the target of every unconditional jump between the previous function's entry and the next
  function that now crosses a function (the `_doMC` case of batch 1). The same command runs after a
  disassembly for every function entry a new jump reaches ("Shared Return Calls" is also an
  instruction analyzer, `SharedReturnJumpAnalyzer`): the new tail call becomes a call-return and
  that function's neighbourhood is scanned the same way. "Function Start Search" names kernel
  call stubs: the language's pattern file (`r5900_LE_patterns.xml` of the Emotion Engine Reloaded
  extension) has `<funcstart label=".." validcode="function"/>` patterns of `li v1,N; syscall;
  jr ra; nop`; the first search of the whole program left a "potential match" mark where no
  function stood, and when a function is added there `FunctionStartFuncAnalyzer` calls
  `SymbolTable.createLabel(.., ANALYSIS)`, which renames the DEFAULT-named function; a second
  pattern of the same bytes adds a label unless a symbol there already contains its text
  (`AddDmacHandler` and `AddDmacHandler2`). The Reference analyzer (`OperandReferenceAnalyzer`)
  looks at every address the new code points to that is undefined: for an address taken (not a
  load or store, nothing reads or writes it) that passes `PseudoDisassembler.checkValidSubroutine`
  (decodes, no data or code in the way, reaches a return, more than one instruction, nothing
  references its inside, not eight zero bytes) it disassembles there with flow following and sets
  a "Found Code" bookmark, and makes no function (its `createFunctions` is empty); otherwise it may
  define a string, a unicode string or a pointer there. Analysis also defines data at the offsets
  new code reads and writes from a base (a table, hardware registers; seen in batch 1 at
  0x443ab4.. and 0x10004004..), which the plan does not list: data defined away from every function body and every map extent still to be made
  is accepted and listed in the report, data defined inside one stops the run (the image is one executable block, so its data areas count as executable memory for the bridge). The plan
  predicts both per disassembly
  (`found_code`, `operand_references`); the apply accepts the predicted code with its bookmark or
  none of it, records `found-code-by-analysis`, and stops on anything else. `eret` has no
  fall-through.
- **Plan** (any worker; reads the release program, writes nothing): `build/release/starts/plan-starts.json`
  and a summary `.md`, deterministic, with its own digest and a baseline (digests of the function
  list, the code gaps, the bookmarks and the defined data). It needs the names plan of the whole
  map made from the current map and the live function list. Per entry: what is there now
  (undefined bytes, instructions, data, references to it), the steps and, per step, the predicted
  instructions, the predicted body of every function the step creates or changes, the jumps it
  turns into calls, or the reason it is withheld. The plan repeats the behaviour above over the
  release image and orders the steps so that every call target, jump target, fall-through
  successor and referenced start is a function first (callee first); creates that need each other
  are withheld. A start is withheld when its bytes do not decode or hold data, its delay slot is
  another function's entry, it calls or jumps to an address that is no function and no map start,
  it references undefined bytes inside another map function, it lies in a gap of another body that
  no create of the plan cuts, a crossing jump would make analysis create a function that is no map
  start, or its flow cannot give the map's extent. A body that differs from the map only by padding
  (nop after a last instruction that falls through, up to the next function) or by unreachable
  words (dead words inside, a `jr ra; nop` after an `eret`) is accepted and marked `accepted` in
  the step; the two existing functions of that kind are accepted as they are. Ghidra's thunk splits
  (a function starting with a branch over its delay slot) cannot be undone with creates and are
  listed. A create whose entry matches a labelled pattern is marked with the name and labels the
  patterns give (`analysis_name`, `analysis_labels`; the plan reads the pattern file and records
  its digest); the summary counts how many equal the prototype counterpart's name. Those names
  stay: the names step later replaces one with the prototype's name for an exact pair, and keeps
  it when the prototype's name is a label at the entry.
- **Apply**: the coordinator only, after a second agent reviewed the plan: the dry run first, then
  `--yes`, optionally `--batch N` entries or, for a pilot, `--only 0x..` (repeatable; plan order,
  and every entry a selected one needs first must be selected too). The same guards as for names (open programs, recorded
  SHA-256, idle analysis, plan digest and map, no unsaved rows, release program only, never a save);
  the program must still match the plan's baseline. After every step the tool waits for idle
  analysis, reads back what the step made (the instructions the disassembly lists and the
  code-unit state of every word of the range and 64 bytes on each side; the new function's body,
  name, signature, flags and the labels at its entry; every cut function's body; every predicted
  call-return as a CALL reference to its target) and compares the whole function list, every code
  gap, every bookmark, every defined data item and a full snapshot of every function (body lowest
  and highest, name, signature line, thunk and no-return: a callee that analysis marks no-return
  shows there) with the prediction. A name the patterns give is accepted and recorded; any other
  name stops the run. Data defined at an address the new code references is listed, not a stop. A
  difference in the end-of-run snapshot is a stop too. Every stop names its kind and what to do:
  `before` (nothing sent for that entry: check, save, confirm, replan), `after` (the write reads
  back otherwise; the program holds it, and a create that failed commits its partial effects:
  close without saving, `--discard-unsaved`, replan; nothing is removed by hand, since removing a
  new function gives a cut container neither its body nor its jumps back), `analysis` (a change the
  plan did not predict: check; save and confirm if acceptable, else close without saving and
  discard). Disassembly is never cleared. Not visible through the bridge: instructions made or
  cleared inside a gap that already held orphan instructions farther than 64 bytes from the step,
  changes inside a body that keep its ends and the union of all bodies, references, and flow
  overrides other than the predicted ones.
- **Save and replan**: as for names. After each batch: `--confirm-saved`, then
  `names.py --plan --all` (it plans names and plates for the new functions; a padded body appears
  there as a boundary difference), then a new starts plan.
- **Record**: `docs/release/ghidra-applied.tsv`, kinds `disassemble` (the instruction range),
  `create` (the body), `extent-accepted` (the body and the accepted difference), `cut-by-analysis`
  (a container's new body after a create inside it), `name-by-analysis` and `label-by-analysis`
  (what Function Start Search gave the new function). Rows stay `unsaved <report>` until
  `--confirm-saved`.

## Stage 3: globals (pairing)

The step after signatures carries the prototype's global names and types into `SCUS_971.34`. Its
first phase pairs the data objects of the two executables; nothing is applied in it:

```powershell
python tools/release/datapair.py              # writes data-map.tsv, DATA.md, build/release/data-map.json
python tools/release/datapair.py --out build/release/<scratch>   # the same files under a scratch folder
```

- **The record**: `docs/release/data-map.tsv` (one row per prototype data object and per release
  data address that code references and no pair covers: release address and size, prototype
  address, size, symbol and section, the release section, class, evidence kinds with their witness
  counts, independent witnesses, flags, owner file) and `docs/release/DATA.md` (counts by class,
  section and module, coverage, the self-check, every witness conflict and contradiction, the
  accesses outside a prototype size). Both are generated, deterministic and never edited by hand;
  `build/release/data-map.json` holds every witness. The report is a file of its own so that
  `compare.py` keeps writing the same function files; rerun `datapair.py` after every `compare.py`
  run, since it reads `function-map.tsv`. It reads both executables, the function map, the
  `@socom-artifact ... socom:data:` annotations under `src/` and `docs/release/settled-data.tsv`;
  nothing from Ghidra.
- **Settled rows**: `docs/release/settled-data.tsv` (release address, `removed` or `-`; prototype
  address or `new`; the prototype symbol, checked against the object; basis; checker; date; optionally
  a withhold reason) is the checker's input, in the spirit of `settled-pairs.tsv`. A row with an
  address or `removed` decides the pair above every other tier (evidence `settled`); evidence that still
  disagrees is listed as a contradiction, not hidden. A row with `-` decides nothing and only carries
  its withhold reason. `--no-settled` ignores the file (to measure the tool alone).
- **Objects**: the prototype's OBJECT and NOTYPE symbols outside the map's functions, aliases at one
  address grouped (the largest size kept; VU microcode labels dropped), plus an anonymous object at
  every address the prototype's code reaches that no symbol holds. An address inside an object pairs
  that object and an offset, never a new object; an address equal to an object's end belongs to it
  when no object starts there.
- **Evidence** (`tools/release/dataflow.py` computes the addresses: a must-analysis of `lui`
  high halves, their low halves, `$gp` offsets and register offsets over each function's own flow;
  on the prototype it agrees with the relocation symbol on 28,911 of 28,914 checkable uses):
  `operand-exact` (the same use at the same position of an exact function pair), `operand-aligned`
  (a deviating pair where the use and every instruction that built its address align: blocks of at
  least four equal masked words that occur once in each function, equal-length stretches of equal
  shapes between two such blocks, or the whole function of an `imm-only` pair; such a use votes only
  after a key check: no key in the same aligned stretch, 32 words either side, may lead elsewhere, a
  key being a callee or an already decided object used once in the function, or the use's own
  distinctive bytes; a use whose neighbourhood of nine instruction shapes recurs in the function
  (repeated code: name lookups, field registrations, destructor records) needs a key that agrees, since
  an insertion in the release can shift such code by whole blocks), `vtable` and
  `named-table` (the function comparison's table pairs), `pointer` (the relocated word at offset k of
  a paired object whose bytes agree up to k+4, pointer words masked and function pointers mapped),
  `content` (bytes found once in each image's data at the prototype's alignment; pointer words
  mapped through the pairs first), `order` (between two paired neighbours of one section at the same
  distance on both sides). One function pair, one paired object or one table is one witness. The
  release `$gp` (0x494670) is what the entry function moves into `$gp`.
- **Decision by tier, not by votes**: tier 0 unique content (8 bytes or more, or a C string) of a
  literal (`@N`), 1 `operand-exact` and tables, 2 such content of other objects and `pointer`, 3
  `operand-aligned` and shorter content, 4 `order`. The strongest tier with witnesses decides: the
  release start is the release address minus the offset of its witnesses with the smallest offset;
  if those disagree the object is `unsure`, `witness-conflict`. Two objects claiming one release start
  keep it only for the one of the strongest tier when it is alone there (`release-shared`). A weaker
  witness that disagrees does not vote: one that points before the start or past the next paired
  release object (or takes the start's address elsewhere) is listed (`contradicted`); one inside the
  object is a field at another offset (`offset-changed`, `offset-outside` past the prototype size).
  Literals rank content first because the release's `GetCommandName` is byte-identical but returns
  the previous string at every case after an inserted enum entry.
- **Classes**: `exact` (same size and the same bytes once pointer words are masked; `.bss` counts as
  zeros; the size is the same when the next prototype object is paired at the same distance, the
  next paired release object starts where the prototype size ends, or a C string's bytes are equal),
  `deviating` (paired, with a difference or a size the evidence only bounds: `size-unconfirmed`,
  `size-changed`, `content-changed`, `pointer-changed`, `offset-changed`, `offset-outside`,
  `section-changed`), `unsure` (a conflict, or a pair on order alone without equal non-zero bytes),
  `new` (a release address code uses that no paired object covers; a field of a new object is a row
  of its own), `removed` (`refs-removed`: only removed functions use it; `refs-unaligned`: paired
  functions use it, not at an aligned place; `unreached`). `identical-copy` marks bytes that occur
  more than once, so content could not decide. Release sizes are `N` when confirmed, else
  `lower..upper`: the furthest release access and the room before the next paired release object.
  A pointer into a function body (a jump table) maps to the same offset of an exact function pair,
  else only into the paired function.
- **For the apply step**: `single-aligned` (the pair rests on one `operand-aligned` witness alone),
  `size-from-release` (a string whose text changed: size and type from the release bytes),
  `constant-as-address` (a witness with no relocation behind it in the prototype), `unrelocated-word`
  (an unrelocated address word that maps through the pairs, compared like a pointer), and the
  `withhold` column with the reason a pair must not be carried: a single aligned witness whose bytes
  differ, an order-only pair whose bytes occur more than once or that paired functions use in the
  prototype but not at an aligned place, or a reason from `settled-data.tsv`.
- **Check** (a second agent that did not change the tool): the self-check in `DATA.md` (every vtable
  and named-table pair against the pairing made without them; an inner table whose offset moved is a
  layout finding); a sample across classes and evidence kinds against both images: the bytes at both
  addresses, and for a code witness the instructions that build the address in both functions; the
  witness conflicts and contradictions read one by one (an enum shift, a deviating function whose
  repeated code aligned wrongly, a release that shares one object between units); `offset-outside`
  and `size-changed` rows against the release code that uses them. The checker's results go into
  the module note that uses the pairs.
- **Not done here**: types (the apply's plan reads them from `socom.elf`, as `signatures.py` does), and
  the apply itself, which needs its own section, review and the user's go-ahead.

## Stage 3: globals (names and types)

The second phase carries the paired objects' names, then types, into `SCUS_971.34` with
`tools/release/globals.py`, through three ordinary bridge writes (no script, nothing cleared or saved):

```powershell
python tools/release/globals.py --plan gamez/zCamera        # or: --plan --all
python tools/release/globals.py --apply build/release/globals/plan-gamez-zCamera.json --dry-run
python tools/release/globals.py --apply build/release/globals/plan-gamez-zCamera.json --yes [--batch N] [--only 0x..] [--check-every N]
python tools/release/globals.py --confirm-saved build/release/globals/plan-gamez-zCamera.apply-001.json
python tools/release/globals.py --discard-unsaved build/release/globals/plan-gamez-zCamera.apply-001.json
```

- **What the bridge does** (plugin 6.0.0 and Ghidra 12.1.4, read from the classes): `create_label`
  refuses a label of the same name at the address and otherwise calls `SymbolTable.createLabel(..,
  USER_DEFINED)` in the global namespace; no code unit changes; a DEFAULT-named function there takes the
  name instead; a dynamic primary (`DAT_`, `PTR_`, `s_`) is deleted and the new label becomes primary,
  otherwise the label is secondary. Symbol events start no analysis. `apply_data_type` resolves the
  type by *name* (well-known names first, then a root type, then the first type of any category with
  that name, case ignored); with `clear_existing` true, the default, it clears the range first, so the
  tool sends false only and the client refuses any other form; `Listing.createData` then refuses, before
  it changes anything, any overlap with an instruction or defined data, analysis `undefinedN` included.
  Pointer components get DATA references to their values (not 0 or all ones, also to addresses no block
  holds), and the new data schedules the data analyzers: only "Data Reference" can act here (it may
  disassemble, or define a string or a pointer, at a target that is undefined bytes or analysis
  `undefined` data; it leaves instructions, strings, pointers and other defined data alone and skips
  addresses outside every block); "Function Start Search After Data" needs `after="data"` patterns,
  which the R5900 pattern file does not have. A primary name starting `g_` can make the naming policy
  refuse a type, so the type goes before the labels. `set_comment` replaces one comment kind. Never sent:
  `set_global` and `apply_data_classification` (they clear), `rename_data` (a naming policy).
- **Labels**: per committed pair of `data-map.tsv`, the prototype program's primary symbol at the
  prototype address (an assembler-local `.dma.1` or `$L..` excepted) and the map's ELF symbol as a second
  label where it differs, as the prototype has them (names that repeat at several addresses stay
  repeated). Literals (`@N`) and anonymous objects get no label and no comment. Withheld, with the
  reason: a map withhold, two committed pairs at one release address, an address no release memory
  block holds, a function (entry or body), an instruction, an address inside a defined data item (an
  offcut label), a stored label there that is no planned one, a release primary in another namespace, a
  prototype symbol outside the global namespace, an invalid name, a name of a release function.
  Unsure, new and removed rows are not named. A one-line plate comment `Release data map: <class> pair
  with prototype <address> <symbol> (evidence ..; flags ..)` goes with the labels unless a plate this tool
  did not write is there; `single-aligned` and the deviating flags show in it.
- **Types**: the prototype's data item at the prototype address, when it is no placeholder
  (`undefinedN`, `undefinedN[k]`, the bare `pointer`, `undefined *`: nothing to carry), the release holds
  the same type at the same path and size and the name resolves to exactly it, the release size is
  confirmed and at least its length (deviating pairs: equal to the prototype size), the flags are none of
  `size-changed`, `offset-outside`, `size-from-release`, the range is undefined bytes, in no function and
  no instruction, overlaps no other paired object, and every pointer component's value is 0, all ones,
  outside every block, an instruction or defined data other than `undefined`. A string takes the length
  to its NUL in the release bytes. A type the release does not hold (an array built on the fly) is
  withheld: applying it would add it to the release type table.
- **Step C** (counted, never built): where a real type would have to replace analysis data, the plan
  counts the objects, bytes, analysis items by kind, the outgoing references a clear would drop and how
  many the new type would make again. Replacing needs a clear; that is the user's decision.
- **Apply**: the coordinator only, after a second agent reviewed the plan: the dry run first, then
  `--yes`, optionally `--batch N` changed entries or `--only 0x..` for a pilot. The same guards as for the
  other steps (open programs, recorded SHA-256, idle analysis, plan digest and map, no unsaved rows,
  release program only, never a save), and the release memory blocks as planned. Per entry, in address
  order: the type, the labels, the comment, each checked first against the state the plan saw or this
  tool's own result, and read back: the data item's type and length, the address's reference count, each
  predicted reference from a pointer component; the primary symbol, type, length, reference count and
  code state after a label, the label in the global list; the comment and the other comment kinds. A light
  snapshot (function list, every defined data item, every stored label, bookmarks) after every type,
  every `--check-every` entries (default 25) and at the end must equal the prediction. Every stop names
  its kind and what to do: `StopBefore` (nothing sent for that entry: save, confirm, replan), `StopAfter`
  (a write answered otherwise or reads back otherwise; a refused type has changed nothing: read, then save
  and confirm or close and discard), `AnalysisStop` (a change the plan did not make: check; save and
  confirm if acceptable, otherwise close without saving and discard).
- **Not handled**: the release program has no memory block for the zero-filled part of its PT_LOAD
  (0x48d200..0x5d6cff, the bss): its pairs get no label or type until a block exists, which is a
  structural change for the user to decide. References, comments and analysis effects inside a range
  other than those listed are not visible through the bridge.
- **Record**: `docs/release/ghidra-applied.tsv`, kinds `data-label`, `data-label-mangled`, `data-type`
  (the type, path and length), `data-comment`; rows stay `unsaved <report>` until `--confirm-saved`, which
  also records a write sent before a stop when the saved program holds it. `--discard-unsaved` refuses
  while the program holds any write the report sent.

## Stage 3: references to globals

Analysis left many accesses from code to globals without a stored reference: it drops a data
reference to an address no memory block holds, and the block `.bss` (0x48d200..0x5d6cff) came
later; for many functions it also had no value of gp yet (`notes/stage3-globals.md`). The step
adds them with `tools/release/references.py`, through one ordinary bridge write (no script, no
analysis, nothing cleared or saved):

```powershell
python tools/release/references.py --plan gamez/zBone        # or: --plan --all
python tools/release/references.py --apply build/release/references/plan-gamez-zBone.json --dry-run
python tools/release/references.py --apply build/release/references/plan-all.json --yes [--batch N] [--only 0x..] [--check-every N]
python tools/release/references.py --confirm-saved build/release/references/plan-all.apply-001.json
python tools/release/references.py --discard-unsaved build/release/references/plan-all.apply-001.json
```

- **What the bridge does** (plugin 6.0.0 and Ghidra 12.1.4, read from the classes):
  `add_memory_reference` (`XrefCallGraphService.addMemoryReference`) calls
  `ReferenceManager.addMemoryReference(from, to, type, source, operand)` in one transaction. It first
  deletes the stack and register references on that operand; the same from, to and operand is never
  duplicated (the type is combined: READ and WRITE give READ_WRITE); a new reference is primary when
  its operand has none. No symbol, data or code unit is made at the target, and auto-analysis reacts
  to no reference event, so nothing runs. The answer is `status success` with the fields and
  `is_primary`, or `{"error": ...}`; type, source and operand in it are echoed from the request, only
  `is_primary` is read from the stored reference, so the answer does not verify the operand or the
  source. There is no undo endpoint, but each write is its own transaction: Edit > Undo in the Ghidra
  window can take back the last ones; the route the tool names stays closing without saving and
  `--discard-unsaved`. `get_xrefs_from` shows target and type only: the operand, source and primary flag
  of a stored reference cannot be read through the bridge. The client sends the write only with type
  READ, WRITE or DATA, source ANALYSIS or USER_DEFINED and an operand of 0 or more.
- **Names a reference brings** (`SymbolUtilities.getDynamicDataName`): a referenced address without a
  symbol shows a dynamic name, `DAT_<address>` (or a data item's own default label, `s_..`, `PTR_..`)
  at an item's start or in no item; inside an item `<item>+<offset>` (offset in decimal below 10, else
  `0x..`), and for a structure or an array the component's path, `<item>.<field>` or `<item>[i]`, where
  `<item>` is the item's primary name. The decompiler then shows that name where it showed a raw
  `uRam..` (`DecompileCallback.lookupSymbol`): expected, so a check that compares decompiler text
  counts it as explained.
- **What analysis makes**, measured on the prototype (every use `dataflow.py` derives in its 9,705
  bodies against every reference Ghidra holds there): a load or store through gp or through a `lui`
  high half gets READ or WRITE on operand 1 (7,224 of 7,224 and 6,640 of 6,640 agree; the right half
  `lwr`/`ldr` of an unaligned pair too, the left half never); an address computation gets a reference
  on itself (15,223, DATA or PARAM), on the store that stores it (1,457), or none. Split by the
  target's block (review `socom-release-refs-review-r6`): into the uninitialised block analysis put
  DATA on the computation whatever the use (bases 719 of 719, other uses 5,533 of 5,537, stored 118 of
  120, gp 254 of 254); into the initialised block a base gets its references on the accesses through
  it (or none), a stored address on the store, other uses PARAM on the computation (gp: 420 of 426).
  A register-offset access is marked in 1,070 of 2,716 cases. The 877 gp references the release holds
  all agree with the derivation.
- **Plan** (any worker; reads the release program, writes nothing): per instruction of a release
  function body (the function holding it) with a use whose target is fixed: the kind, the reference
  (from, to, type, operand), the instructions that build the address, what the instruction holds
  already, and the target's block, labels, defined data with the offset in it, data-map row with the
  offset, and code-unit state. Made: `gp-load`, `pair-load` READ operand 1; `gp-store`, `pair-store`
  WRITE operand 1; `gp-address`, `pair-address` DATA operand 0 into the uninitialised block, and
  `gp-address` into the initialised block only for another use (no base, not stored) and as the
  function's one reference to that target, where analysis without gp missed the PARAM it makes
  (operand 0 is the destination register, which the
  analyzer's operand search matches; PARAM is not made, since analysis deletes PARAM references of any
  source when it revisits an instruction). Source ANALYSIS (`--source-type USER_DEFINED` at plan time
  for the other); a re-analysis removes neither. Present: a reference to the target from the
  instruction exists; covered: an address the function stores, where the store has the reference.
  Withheld, with the reason: register-offset accesses, the left half of an unaligned pair, a
  `lui`/`ori` pair (a constant: all 17 in the prototype), the value of gp itself, a target outside
  every memory block, a load or store into code, an address into code that is no function entry, an
  instruction that already has another reference (its operand cannot be read), a `lui` pair address
  into the initialised block (the release analyzer had the block and the pair and chose not to mark
  it), and a gp address into the initialised block used as a base, stored, or as a second reference of
  the function to its target (a reference the program holds from another of its instructions).
  Indexed accesses have no fixed target and are counted. An address computation lists what the
  function does with the address (`feeds`: accesses through it, field or indexed; a store). Not
  derived: references through pointers analysis read from initialized memory, values stored as
  addresses no computation of the function builds.
- **Review**: a second agent that did not write the plan checks it before anything is applied.
- **Apply**: the coordinator only, after the review: the dry run first, then `--yes`, optionally
  `--batch N` references or `--only 0x..` (the instruction) for a pilot. The same guards as the other
  steps (open programs, recorded SHA-256, idle analysis, plan digest and function map, no unsaved rows,
  release program only, never a save) and the memory blocks as planned. Per reference: the references
  from the instruction must be those the plan saw (with the planned one too: unchanged, a second run
  changes nothing), the function holding it must have the planned entry and body, the target the
  planned type, length and code state; then one write, whose answer must echo the request with
  `is_primary` true; the references from the instruction must read back as before plus exactly the
  planned one, the references to the target as before plus this one, and nothing else of the target
  changed (where it had no name, the dynamic name above: at an offset inside a data item only the
  offcut forms of that item). A snapshot of every function (body, name, thunk, signature line,
  no-return), every defined data item, every stored label, every bookmark, the state and the whole
  reference list of every target written so far, and the references from every planned instruction
  met in the run is compared with the expected one after every `--check-every` writes (default 250),
  whenever analysis is seen running after a write, and at the end. Stops as in the globals step:
  `StopBefore` (nothing sent for that reference: save, confirm, replan), `StopAfter` (the write
  answered or reads back otherwise: read it; save and confirm, or close without saving and discard),
  `AnalysisStop` (a change the plan did not make: check it first); after a write, Edit > Undo can also
  take back the last references, as above.
- **Record**: `docs/release/ghidra-applied.tsv`, kind `reference`, the row at the instruction's
  address, the value `to <target> <type> operand <n> <source> (<kind>)`; rows stay
  `unsaved <report>` until `--confirm-saved`, which also records a write sent before a stop when the
  saved program holds it; `--discard-unsaved` refuses while the program holds any reference the
  report sent.
- **Not visible through the bridge**: the operand index and source of a stored reference (a pilot
  checks them in the Ghidra window), and the listing's operand display.
