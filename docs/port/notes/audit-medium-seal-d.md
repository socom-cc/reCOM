# Audit of list medium-seal-d (2026-11-19, socom-port-audit-mseal-d)

98 functions (36,780 bytes) in six zSeal files: `seal_body.cpp` 35, `seal_kit.cpp` 44,
`seal_airesponse.cpp` 9, `seal_create.cpp` 6, `seal_command.cpp` 2, `seal_ailines.cpp` 2. HEAD
b3fe23ed, then e0270b9a (medium-seal-b merged; it touches none of these files). Judged file by file
(seal_body first, it held the top of the scan), each over its whole address range against the
packet's disassembly; every address quoted below and every delay slot relied on was checked in
`build/port/boot-auditkit/ref.dis` (the packets' compacted listings drop instructions, so a
branch's address counted from a packet is off by one or two words).

## What the packets lacked

- Branch addresses: the compacted listings drop words (often a nop), so addresses counted from a
  packet were off by 4 or 8 in six of the first rows; all were re-read from ref.dis.
- Layouts of objects written through other registers: CLightMap / CLight (DWARF, `dw.py`), the
  CZKit bitfield order (the packets label byte 0 / 1 of CZKit with the wrong members), AI_REACTION.
- Callee state the stale reasons depended on: whether CSealUnit::CreateSinglePlayerUnits and the
  CLightMap ctor are written (grep), and CSealUnit::AllowCommand's signature.
- The bodies of the helpers called through other objects: CBody::BodySetState vs CZSealBody's,
  ClearStack, GetObjAnim, the SetMoving* overlay helpers, CMatrix::Transform's order.
